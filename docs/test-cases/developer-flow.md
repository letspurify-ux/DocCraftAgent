# 신규 개발자 로직 흐름 문서 — 실제 테스트 기준

대상은 `/Users/iceblue/workspace/llm_agent`, 결과 파일은 `/Users/iceblue/workspace/llm_agent_developer_flow.md`이다. 기존 관리자 매뉴얼은 덮어쓰지 않는다. 저장된 LLM을 사용하며 추론 off, 출력 16,384토큰, 요청별 컨텍스트 최대 200k, 실행 토큰 한도 10,000,000, 검토 3회로 테스트한다.

## 독자의 목표

처음 합류한 개발자가 사용자 질문 하나의 전체 처리 경로를 설명하고, 잘못된 결과나 중단 문제를 어디에서 추적할지 알 수 있어야 한다. 4~5개 장으로 전체 개념 → 정상 요청 추적 → 주요 분기와 실패/취소 → 소스 읽기와 디버깅 순서를 연결한다. 전체 시퀀스 다이어그램 하나와 필요한 핵심 분기 다이어그램 하나를 사용한다. 작업의 `max_diagrams`는 2로 설정한다. 최종 재검증에서는 아래 진입 파일·심볼을 생성 방향의 검색 힌트에도 명시했다. 따라서 초기 초안과의 비교에는 프로그램 수정뿐 아니라 테스트 입력 구체화도 포함된다.

## 소스와 대조할 핵심 경로

- `frontend/src/App.jsx`: 전송 직전 history 확정, `/api/chat` 요청, NDJSON 이벤트 소비, 세션 전환 및 AbortController 처리.
- `backend/src/server.js`: 입력 정규화·검증, 요청 단위 취소 신호, `handleQuestion`, 응답용 trace 정리, 정상·오류·취소 기록의 구분.
- `backend/src/agent.js`: `decideSafe`의 결정을 따른 루프. 모든 질문이 반드시 검색 또는 SQL 실행을 거친다고 설명해서는 안 된다.
- `answer`, `search`, `expand`, `read_result`, `run_query`/`run_queries`: 행동별로 무엇을 읽고 변경하며 언제 다시 LLM 판단으로 돌아가는지 구분한다.
- `runSearch`/`selectQueries`: 처리방법이 언급한 등록 쿼리와 직접 검색한 쿼리를 합치는 실제 경로 및 중복 제거. 임의 SQL 생성과 등록 쿼리 실행을 혼동하지 않는다.
- 루프 종료: 정상 answer, 시간·횟수·이력·반복 가드, 강제 답변 및 fallback의 구분. 취소를 정상 fallback으로 설명하지 않는다.
- 결과 반환: 내부 추적 기록과 화면용 trace, 전체 결과 행, 최종 answer와 진행 이벤트를 구분한다.

이 목록은 현재 소스의 사전 대조 기준이다. 생성 결과는 실행에 고정된 소스 스냅샷과 다시 대조한다.

## 결과물 합격 기준

1. 첫 장을 읽고 시스템의 목적·주요 역할·하나의 전체 경로를 이해할 수 있다.
2. 이후 장이 앞 장의 입력·결정·결과를 이어받는다. 함수·파일별 독립 설명의 모음으로 돌아가지 않는다.
3. 시퀀스 다이어그램의 화살표, 조건, 반복 및 종료가 구현 근거와 일치한다.
4. 중요한 실행·검색·결과 읽기·취소 분기가 누락되지 않는다. 확인하지 못한 연결은 구분한다.
5. 가상 입력을 실측 결과로 표현하지 않는다. 리뷰 대화, 소스 수정안, 설치/관리 백과사전이 본문에 섞이지 않는다.
6. 각주가 실제 소스 위치를 가리키며 Mermaid가 파싱·표시된다.
7. 주요 미해결 지적과 분석 범위 제한은 숨기지 않는다. 자동 검토 결과 외에 결과물을 직접 읽고 소스와 표본 대조한다.
8. 부족한 부분을 발견하면 생성 프로그램을 수정하고, 관련 회귀 검사 및 실제 결과 재검토로 확인한다.

## 외부 전송 범위

실제 생성은 소스의 선택된 코드 청크와 작성·검토 문맥을 저장된 OpenRouter 엔드포인트로 전송한다. `.env*`, seed SQL, 잠금 파일, minified 파일과 sourcemap은 작업 제외 패턴에 포함한다. 실제 호출은 외부 전송 승인 이후 진행한다.
